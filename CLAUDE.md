# Contexto do projeto — Financeiro Web

Frontend do sistema de controle financeiro pessoal. Consome a API em `financeiro-api` (projeto irmão, Spring Boot). Este arquivo dá contexto rápido ao Claude Code sobre decisões já tomadas.

O usuário organiza os dados em **abas** (ex: uma por banco — BTG, Itaú...) — cada aba é uma cópia independente do sistema (categorias, gastos, devedores, período fiscal próprios). A tela inicial (`HomePage`) é um gráfico de rosca com uma fatia por aba (proporcional ao gasto do período) e "Visão Geral" clicável no centro, que soma todas as abas.

## Stack e por quê

- **React 18 + TypeScript + Vite** — escolhido por ser o mais pedido em vagas (decisão do usuário, mesmo raciocínio do backend em Java).
- **TailwindCSS**, com **tokens de design via CSS custom properties** (ver seção de conceito visual) — permite dark mode automático sem duplicar classes `dark:` em todo lugar.
- **React Router** pra navegação, **Axios** com interceptor de JWT.
- **Sem gerenciador de estado global** (Redux/Zustand) — o app é simples o suficiente pra `useState`/`useCallback` local em cada página + `AuthContext` pra sessão. Se o app crescer bastante, reavaliar.

## Conceito visual: estilo iOS Wallet/Health (trocado a pedido do usuário)

O conceito original era um "livro-caixa analógico" (papel, tinta, serifada Fraunces) — foi **descartado deliberadamente** a pedido do usuário, que queria algo "mais jovem, parecido com os layouts da Apple". Não reintroduzir o visual antigo (papel bege, Fraunces, `.ledger-row`) sem confirmar antes.

- **Cores** (`tailwind.config.js` + variáveis CSS em `index.css`): tokens `bg`/`surface`/`surface-soft`/`line`/`ink`/`ink-soft`/`accent`/`success`/`danger`/`warning` (+ variantes `-soft` pra fundos de pill/badge). Cada token é `rgb(var(--color-x) / <alpha-value>)`, com os valores das variáveis redefinidos em `:root.dark` — isso é o que permite o dark mode funcionar em toda a UI sem prefixo `dark:` espalhado pelo código.
- **Tipografia**: pilha de fonte do sistema Apple (`-apple-system, BlinkMacSystemFont`) com `Inter` (Google Fonts) como fallback pra quem não estiver no macOS/iOS. Sem serifada, sem monospace — números usam `.num` (tabular-nums + semibold na própria sans), não uma fonte separada.
- **Layout**: cards com `rounded-3xl` (`.card` em `index.css`), listas com `divide-line/70` dentro do card ao invés de bordas soltas, botões `rounded-full` (`.btn-primary`/`.btn-secondary`), modais como bottom-sheet no mobile (`rounded-t-3xl`) e centralizados no desktop.
- **Dark mode**: classe `.dark` na tag `<html>`, controlada por `ThemeContext` (`src/context/ThemeContext.tsx`), persistida em `localStorage` (`financeiro_theme`) e com um script inline no `index.html` que aplica a classe antes do React montar (evita flash do tema errado).
- **Ícones**: SVGs desenhados à mão em `src/components/icons.tsx` (sem dependência tipo lucide-react) — estilo de traço fino, arredondado, inspirado em SF Symbols.

**Se for adicionar uma tela nova, seguir esse padrão** — usar `.card`, os tokens de cor, e os ícones existentes; não introduzir cores hardcoded fora da paleta ou uma fonte serifada de volta.

## Decisões de produto (espelham o backend)

1. Gastos e Devedores são módulos independentes, cada um com seu próprio período fiscal (dia de fechamento configurável) — e **por aba**: cada aba tem sua própria config. O usuário escolhe o período diretamente clicando na data no `PeriodNavigator` (abre um `<input type="month">` nativo sobreposto ao label), além de navegar mês a mês com as setas.
2. Categorias são customizáveis (nome + cor, paleta vibrante estilo tags do iOS) — sem seed fixo, únicas por aba.
3. Dívidas têm 3 status (`pendente`/`parcial`/`quitado`) com cores próprias (ver `STATUS_CLASS` em `DevedorDetailPage.tsx`, usa os tokens `danger`/`warning`/`success`).
4. Abas: criar/renomear/recolorir/excluir (`CreateTabModal.tsx`, `ManageTabsModal.tsx`) — excluir a última aba é bloqueado pelo backend. A Visão Geral funde categorias/pessoas de mesmo nome entre abas diferentes numa linha só (decisão do usuário) e não permite lançar dado nela (é só leitura — pra lançar algo, precisa estar dentro de uma aba específica).

## Roteamento (três "famílias" de tela)

```
/                           -> HomePage (dentro de HomeLayout: topo simples, sem nav de Gastos/Devedores)
/visao-geral                -> OverviewPage (idem, HomeLayout)
/tabs/:tabId/gastos         -> GastosPage (dentro de AppLayout: sidebar com Gastos/Devedores da aba)
/tabs/:tabId/devedores      -> DevedoresPage
/tabs/:tabId/devedores/:id  -> DevedorDetailPage
/bets                       -> BetsHomePage (dentro de BetsLayout: própria topbar, nada a ver com Financeiro)
/bets/months/:monthId       -> BetMonthDetailPage (idem)
```

`AppLayout` busca `GET /tabs` pra descobrir o nome da aba atual (via `tabId` do `useParams`) e mostrar no lugar do wordmark "Financeiro" no topo da `Sidebar` — esse wordmark/ícone de casa é o link de volta pra `/`. Toda página dentro de uma aba lê `tabId` via `useParams` e prefixa as chamadas de API com `/tabs/${tabId}/...`; os modais (`AddExpenseModal`, `AddDebtModal`, `AddDebtorModal`, `ManageCategoriesModal`, `PeriodSettingsModal`, `RegisterPaymentModal`) recebem `tabId` como prop pro mesmo fim.

## Estrutura

```
src/
  api/          # client.ts (axios + interceptor JWT), types.ts (espelha os DTOs do backend)
  context/      # AuthContext (login/registro/logout, hidrata via GET /auth/me), ThemeContext (dark/light)
  components/   # Sidebar, AppLayout, HomeLayout, DonutTabChart, modais (Add*, Manage*, Create*, PeriodSettings), CategoryBar (genérico: categoria OU aba), icons.tsx
  pages/        # Login, Register, Home (radial), Overview (visão geral), Gastos, Devedores, DevedorDetail
  utils/        # format.ts (formatCurrency, formatDate, formatMonthName — sempre pt-BR), colors.ts (paleta de cores compartilhada categorias/abas)
```

Padrão de página: cada página de dados busca tudo via `useCallback` + `useEffect`, guarda em `useState` local, e re-chama `load()` depois de qualquer mutação (criar/editar/excluir) ao invés de atualizar o estado otimisticamente. Simples e suficiente pro tamanho atual do app.

## `DonutTabChart` — o gráfico de rosca da tela inicial

SVG puro (sem lib de gráfico), em `src/components/DonutTabChart.tsx`. Cada aba vira uma fatia cujo ângulo é proporcional a `totalGastoPeriodo` (vindo de `GET /dashboard/visao-geral`), com um piso mínimo de 8° pra aba com R$0 continuar visível/clicável — sem isso ela sumiria do gráfico. É uma rosca (donut), não uma pizza cheia, de propósito: sobra espaço no centro (a "rosquinha") pra um botão HTML absolutamente posicionado por cima do SVG ("Visão Geral" + total), sem competir com o hit-test das fatias.

## Gastos recorrentes e dívidas parceladas

Cada ocorrência/parcela é uma linha **real** e independente (o backend materializa tudo na criação, ver `financeiro-api/CLAUDE.md`) — o frontend não faz nenhuma projeção, só reflete o que veio da API, igual sempre fez.

- **Criar**: `AddExpenseModal.tsx` ganhou um seletor "Recorrência" (`Só esse` / `Por X meses` / `Indefinida`, três botões tipo os toggles Saque/Depósito do Bets) — quando não é "Só esse", manda `recurrence`/`recurrenceMonths` no POST e o label do campo de valor vira "Valor mensal". `AddDebtModal.tsx` ganhou um checkbox "Parcelar" que revela "Quantas vezes" com uma prévia ao vivo (`R$ X,XX/mês`, calculada no frontend só pra exibição — o backend é quem faz a divisão de verdade) e troca o label do valor pra "Valor total".
- **Editar**: `EditExpenseModal.tsx`/`EditDebtModal.tsx` (novos, ao lado dos Add que só criavam — **antes dessa feature não existia edição de gasto/dívida no frontend, só criar e excluir**) têm os mesmos campos dos Add, mais um checkbox "Aplicar às [próximas ocorrências/parcelas futuras] também" que só aparece quando `expense.recurringGroupId`/`debt.installmentGroupId` não é `null`. Quando marcado, o campo de data fica desabilitado (mudar a data de "todas as futuras de uma vez" não faz sentido — cada uma mantém a sua) e manda `applyToFuture: true` no PUT.
- **Excluir**: `GastosPage.tsx`/`DevedorDetailPage.tsx` só abrem o `ConfirmDeleteRecurringModal.tsx` (componente novo, compartilhado pelas duas telas) quando o item tem `recurringGroupId`/`installmentGroupId` — perguntando "excluir só esse/essa" vs. "esse/essa e os/as futuros/as" (manda `applyToFuture` como query param no DELETE). Sem grupo, continua excluindo direto sem perguntar, como sempre foi.
- **Badges**: gasto recorrente mostra uma `.pill` "Recorrente" ao lado da descrição em `GastosPage.tsx`; parcela de dívida mostra "Parcela X/Y" ao lado do status em `DevedorDetailPage.tsx` (usa `installmentNumber`/`installmentTotal` vindos da API).

## Módulo Bets — área separada, fora do layout do Financeiro

Ativado por `user.betsEnabled` (toggle no `SettingsModal.tsx`, ao lado do dark/light). Não tem nada a ver com abas — é uma segunda "aplicação" dentro do mesmo app React, com seu próprio layout (`BetsLayout.tsx`: topbar "Bets" + botão pra voltar ao Financeiro + Configurações + Sair, sem `Sidebar`/`AppLayout`).

- `BetsLayout` faz o guard de acesso: se `user.betsEnabled` for `false`, redireciona pra `/` (`<Navigate to="/" replace />`) — mesma ideia do `ProtectedRoute`, mas checando a flag em vez da sessão.
- `HomeLayout.tsx` mostra um ícone "Bets" (`TrendingUpIcon`) do lado do de Configurações **só se** `user.betsEnabled` — é o único ponto de entrada no fluxo normal do Financeiro; o caminho de volta é o ícone `WalletIcon` dentro do `BetsLayout`.
- **Painel em funil** (pedido explícito do usuário, "como a Apple faria"): `BetsHomePage` mostra só o lucro total (`GET /bets/overview` — soma o `profitLoss` de todos os meses, ver `BetService`) + a lista de todos os meses (`GET /bets/months`), cada um no seu **próprio `.card`** (pedido do usuário — igual os dias, não uma lista dividida por linhas), com um ícone de excluir (`DELETE /bets/months/{id}`, com `window.confirm` antes — é o único `confirm()` nativo do app, os outros delete não confirmam, mas apagar um mês inteiro é bem mais destrutivo). Clicar num mês **navega** pra `BetMonthDetailPage` (`/bets/months/:monthId`) — decisão do usuário, prefere tela própria a expandir inline (fica pesado com 30 dias). **O lucro total do topo sempre bate exatamente com a soma dos meses listados abaixo dele** — e o de cada mês sempre bate com a soma das casas dele (ver próximo ponto); já foi motivo de bug relatado (números divergindo quando tinha ajuste manual de saldo) e agora as duas telas somam da mesma fonte.
  - **Agrupado por ano** (pedido explícito do usuário): a lista de meses é dividida em blocos por ano (`startDate.slice(0,4)`), cada bloco com um total DAQUELE ano (soma do `profitLoss` dos meses dele, em R$) convertido em unidades **pela unidade atual** (`overview.currentUnitValue`, vindo pronto do backend) - não soma a unidade já calculada de cada mês (mesmo motivo do `totalProfitLossUnits` do overview: a unidade muda com o tempo). Como `months` já vem mais-recente-primeiro da API, agrupar com um `Map` preservando a ordem de inserção já deixa os anos do mais recente pro mais antigo, sem precisar ordenar de novo. **Cada ano é o seu próprio `.card`, igual um mês/dia** (pedido explícito do usuário, "como se fosse um mês que é hoje") - começa **recolhido** (`expandedYears: Set<string>` vazio no início, mesmo padrão accordion dos dias/do "Geral do mês"), mostrando só o total em unidades no cabeçalho clicável; ao abrir, revela os cards dos meses daquele ano dentro de uma área recuada (`bg-surface-soft`, mesmo visual do dia expandido em `BetMonthDetailPage`).
- Dentro do mês, cada dia é o seu **próprio `.card`** (pedido do usuário — "quero separado, cada um no seu retângulozinho", não uma lista dividida por linhas) e começa **recolhido** (`expanded: Set<string>` vazio no início — nada de auto-expandir "hoje" ou todos os dias; só abre no clique). A ordem de exibição é **decrescente, dia mais recente primeiro** (pedido explícito do usuário, trocado de "dia 1 primeiro") — o array que vem do backend (`data.days`) já é mais-recente-primeiro (é o mesmo que `data.days[0]` usa pra "unidade atual"), então a página usa ele **direto**, sem inverter nada. Cada casa mostra "início → final" do dia. **Editar (ícone de lápis) aparece em qualquer mês, aberto ou fechado** — só fica escondido pra um dia futuro (placeholder de "amanhã já criado", `day.date > hoje`), já que não dá pra saber o resultado de uma aposta antes dela acontecer.
  - **Destaque da última casa atualizada** (pedido do usuário, "padrão Apple", pra não se perder depois de editar um saldo no celular): ao salvar o `UpdateBetBalanceModal`, a página guarda `{houseId, date, at: Date.now()}` num state `lastUpdate` ANTES de recarregar. A linha da casa correspondente ganha a classe `.flash-highlight` (`index.css` - `@keyframes` que anima `background-color` do `accent-soft` até transparente em 1.6s, depois some sozinha). O `at` (timestamp) entra na `key` do elemento só quando ele é o destacado - isso força o React a remontar aquela linha específica se a MESMA casa for editada de novo em seguida, reiniciando a animação do zero (sem isso, o CSS não reanima porque a classe não muda entre renders).
- **Card "Geral do mês, por casa"** (acima da lista de dias): soma do resultado de cada casa ao longo do mês inteiro (`data.houseSummaries`, já vem pronto do backend — a página só formata). `data.profitLoss`/`profitLossUnits` no topo do mês **é** a soma dessas casas (mesma fonte no backend) — os dois números sempre batem, incluindo quando tem dia negativo. Também é **recolhível, começando fechado** (`geralOpen` local, mesmo padrão accordion dos dias) — o card em si sempre aparece (se tiver alguma casa), só a lista de casas dentro é que fica escondida até clicar. **Só aqui** (não no card de cada dia) as casas ficam ordenadas da mais lucrativa pra menos lucrativa (`.sort((a,b) => b.totalResult - a.totalResult)`) — pedido explícito do usuário. Ordena separadamente: casas sem grupo entre si, casas dentro de cada grupo entre si, e os grupos entre si (pelo total do grupo) — não interlaça grupo com casa solta numa lista só, cada seção mantém sua própria ordenação por lucro.
- **`StartBetMonthModal` pede mês/ano** (`<input type="month">`, nativo — sem lib de date picker), não só o valor da unidade: dá pra escolher o mês atual, um mês passado (backfill, entra como registro separado sem mexer no mês aberto — mostra um aviso diferente nesse caso, calculado no frontend por `isFullyPast()`) ou um mês futuro (vira o mês corrente na hora, mesmo o calendário não tendo chegado nele ainda).
- **`Modal.tsx` (base de TODOS os modais do app, não só Bets)**: o fundo escuro só fecha o modal se o gesto INTEIRO (`mousedown` **e** `click`) começou e terminou nele mesmo (`e.target === e.currentTarget` nos dois, guardado num `useRef` entre os dois eventos) — **bug já corrigido**: antes, só comparava `onClick` com `stopPropagation()` no conteúdo, e selecionar/arrastar pra marcar todo o texto de um campo (ex: o valor de um saldo) podia terminar o clique (mouseup) fora do card do modal, fechando ele sem querer no meio da edição. Também trava o scroll do `body` (`position: fixed` + `top: -scrollY`) enquanto está aberto e restaura a posição exata ao fechar — **bug já corrigido**: no celular, o teclado abrindo/fechando pra editar um campo numérico deslocava a página de fundo, e ela não voltava pro lugar certo depois de fechar o modal.
- Modais: `CreateBetHouseModal`/`ManageBetHousesModal` (cópia do padrão `CreateTabModal`/`ManageTabsModal`, mas essa busca as casas sozinha via `GET /bets/houses` em vez de receber por prop, porque também cuida da reordenação), `UpdateBetBalanceModal` (props explícitas `monthId/houseId/houseName/date/currentBalance/startOfDayBalance/currentOpeningOverride`; a rota de salvar leva `monthId` — `POST /bets/months/{monthId}/houses/{houseId}/balance`, não infere mais "o mês aberto"). Tem DOIS campos — "saldo inicial do dia" e "saldo final do dia" — pra permitir registrar um depósito/saque na casa sem contar como resultado de aposta. **Não usa mais um booleano de "touched"** pra decidir se manda o ajuste do saldo inicial (era frágil, causava o campo "perder" o valor sem motivo claro) — em vez disso, compara o valor **submetido** com o valor que veio como padrão (`startOfDayBalance`, prop): se bater (campo não mudou), reenvia `currentOpeningOverride` (o ajuste explícito que já estava salvo pra esse dia, ou `null` se já era automático); se for diferente, manda o valor novo digitado como ajuste explícito. **Bug já corrigido**: antes, quando o campo não mudava, sempre mandava `null` — isso apagava um ajuste explícito que já existia (ex: editar só o "saldo final" de um dia com saldo inicial ajustado por um saque/depósito zerava esse ajuste), porque não tinha como saber se o valor mostrado vinha do carry-forward automático ou de um ajuste real. `currentOpeningOverride` vem de `BetMonthDayHouse.openingOverride` (novo campo do backend, espelha o `bet_daily_balances.opening_balance` bruto — `h.balance - h.result` continua sendo o valor CALCULADO/mostrado, não confundir os dois). `StartBetMonthModal`, `ChangeUnitValueModal` (mostrado dentro de `BetMonthDetailPage`, não mais na Home).
- **Saque/Depósito** (`TransferModal.tsx`): botão "Saque / Depósito" dentro de cada dia expandido (não dentro do editor de saldo por casa — pedido explícito do usuário, "esse botão n precisa ficar dentro de onde cadastra o valor da casa"), visível só pra `day.date <= hoje`. O modal tem um toggle Saque/Depósito (troca os labels e o texto explicativo) e **dois** `<select>` com todas as casas do dia: "De qual casa"/"Pra qual casa" (a casa de aposta) e "Pra qual conta"/"De qual conta" (a outra ponta — **não é mais fixo numa casa chamada "Banco"**, a pessoa escolhe, porque tem gente com mais de uma conta/banco). `defaultCounterpart()` continua pré-selecionando uma casa chamada "Banco" se existir (mantém o caso comum rápido, sem clique extra), senão cai pra primeira casa disponível diferente da selecionada — e os dois `<select>` se auto-ajustam pra nunca deixar escolher a mesma casa dos dois lados. O texto explicativo usa o **nome real** da conta escolhida (`"Tira o valor da casa e coloca em \"BTG\"..."`), não mais a palavra fixa "Banco". Envia `counterpartHouseId` no corpo de `POST /bets/months/{monthId}/houses/{houseId}/transfer`. Erro (ex: escolher a mesma casa nos dois campos) aparece via `extractErrorMessage`, mesmo padrão dos outros modais.
- **Agrupamento de casas** (pedido do usuário: juntar várias sub-contas de uma mesma casa mãe, ex: divisões da Bet365, e ver o resultado combinado): gerenciado dentro do `ManageBetHousesModal` — o painel de edição de cada casa ganhou um `<select>` "Grupo" (busca `GET /bets/groups` no mount) com "Sem grupo", os grupos existentes, e "+ Criar novo grupo…" (revela um campo de nome; ao salvar, cria o grupo via `POST /bets/groups` primeiro e só depois associa a casa via `PUT /bets/houses/{id}/group`). Casas com grupo mostram uma `.pill` com o nome do grupo na listagem. Em `BetMonthDetailPage`, tanto "Geral do mês, por casa" quanto cada dia expandido usam o helper `splitByGroup()` (separa `groupId != null` de `null`) pra renderizar cada grupo como um bloco com o subtotal (`data.groupSummaries` no mês, `day.groups` no dia) e as casas-membro indentadas por baixo — casas sem grupo continuam soltas como sempre, e o botão "Editar" de cada casa continua funcionando normalmente mesmo dentro de um grupo. **Cada bloco de grupo começa fechado** (mesmo padrão accordion do resto do app — dias, "Geral do mês"): um `expandedGroups: Set<string>` guarda as chaves abertas, com chave `month:{groupId}` pro bloco do resumo do mês e `day:{date}:{groupId}` por dia — assim expandir o grupo no mês não expande ele em cada dia (e vice-versa), do mesmo jeito que cada dia expande independente dos outros.
  - **Banca por grupo no topo do mês** (pedido explícito do usuário): logo abaixo da linha "banca: R$X" no cabeçalho de `BetMonthDetailPage`, uma linha extra (só aparece se `data.groupSummaries.length > 0`) lista `{grupo.name}: {formatCurrency(grupo.banca)}` pra cada grupo - `banca` é campo novo do backend (saldo atual combinado do grupo, não resultado do mês). Fica fora do card "Geral do mês, por casa" (que é sobre resultado/lucro, não banca) e sempre visível, sem accordion, já que são só uma ou duas linhas curtas.
  - **Mesma coisa na Home** (pedido explícito, "coloca também pra aparecer no início, sem ser no mês... com menor destaque"): `BetsHomePage` mostra `overview.groupBanca` na mesmíssima posição/estilo - logo abaixo da linha "banca: R$X · Yun" do card "Lucro total" (`text-xs text-ink-soft`, igual ao do mês).
- **Competição** (`BetCompetitionsPage.tsx` lista as competições que a pessoa participa — criadas ou entradas — com uma `.pill` "Sua" nas que ela criou; `BetCompetitionDetailPage.tsx` é o ranking): entrar ponto no `BetsHomePage` via botão "Competições" (ícone `UsersIcon`). `CreateCompetitionModal` (nome + `<input type="month">`, mesmo padrão do `StartBetMonthModal`) navega direto pro ranking recém-criado ao salvar; `JoinCompetitionModal` (campo de código, maiúsculas forçadas com `.toUpperCase()`) faz o mesmo. No ranking: o código aparece num card clicável com `navigator.clipboard.writeText()` (feedback "Copiado!" por 2s, sem tratamento se falhar — clipboard pode não estar disponível, não é crítico) pra convidar mais gente, e a lista usa emoji de medalha (🥇🥈🥉) pras 3 primeiras posições, senão só o número. Cada linha mostra **só unidades** (pedido explícito do usuário — diferente do resto do app, aqui NÃO mostra R$, `entry.profitLoss` fica no DTO mas o componente não usa), destaca a própria linha (`entry.isYou`) com um fundo suave e uma `.pill` "Você", e mostra "Sem mês registrado nesse período" pra quem não tem `hasData` em vez de simplesmente sumir da lista.
  - **Expandir uma pessoa mostra os últimos 3 dias** (pedido explícito do usuário, mesmo padrão accordion do resto do app): cada linha vira um `<button>` (em vez de só o `<li>` estático) com `aria-expanded` e chevron que gira, controlado por `expanded: Set<string>` (vazio no início - começa fechado, igual dias/anos/"Geral do mês"). Só é clicável se `entry.recentDays.length > 0` (`canExpand` - sem chevron nem cursor de clique senão). O conteúdo expandido é só `date` + `resultUnits` de cada dia (`day.result` em R$ vem no DTO mas não é usado, mesmo critério de "só unidades" do resto da tela) - já vem pronto do backend dentro da própria resposta do ranking, sem chamada extra à API.
- **Amigos - tentado e removido**: chegou a existir uma tela de amizade (código pessoal pra convidar, convites recebidos, resultado do mês atual por casa de quem aceitou) - `BetFriendsPage.tsx`, `BetFriendDetailPage.tsx`, `AddFriendModal.tsx`. Testada pelo usuário em produção (chegou a adicionar o thiago de verdade) e depois removida por decisão dele, sem problema técnico encontrado. Ver `financeiro-api/CLAUDE.md` (seção Bets) pro porquê a migration do backend continua no repo mesmo com a feature removida.
- **Reordenar casas** (arrastar, estilo Apple): em `ManageBetHousesModal`, cada linha tem uma alça (`GripIcon`) com handlers de `onPointerDown`/`onPointerMove`/`onPointerUp` — sem lib de drag-and-drop, só `setPointerCapture` pra garantir que os eventos de mover/soltar continuem chegando na alça mesmo com o ponteiro fora dela, e troca de posição na lista local quando o ponteiro cruza o meio de uma linha vizinha. Ao soltar, `PUT /bets/houses/reorder` com a nova ordem de ids.
- **"Excluir" uma casa arquiva, não apaga de verdade** (pedido explícito do usuário): `ManageBetHousesModal` separa `houses` (tudo que veio de `GET /bets/houses`) em `activeHouses` (`archivedFrom == null`, lista arrastável/editável de sempre) e `archivedHouses` (mostradas numa seção separada abaixo, sem drag nem editar, só com "desde DD de mês de AAAA" e um botão "Restaurar"). O botão de excluir (ícone X) continua chamando `DELETE /bets/houses/{id}` normalmente — só que agora esse endpoint arquiva no backend em vez de apagar. `PUT /bets/houses/{id}/restore` desfaz. O drag-and-drop (`handlePointerMove`/`handlePointerUp`) opera só em cima de `activeHouses` (não a lista completa) - ao reordenar, os arquivados voltam pro final da lista completa antes de salvar no state, já que a ordem deles não importa mais.
- `formatUnits()` em `utils/format.ts` formata em "X,XX un" (pt-BR, 2 casas).

## Cuidado com `toISOString()` pra pegar "a data de hoje"

`new Date().toISOString().slice(0, 10)` converte pra UTC antes de formatar - a partir das 21h no horário de Brasília, já retorna a data de amanhã (bug real relatado pelo usuário, espelhava o mesmo problema do backend rodando em UTC no Render - ver `financeiro-api/CLAUDE.md`). O `todayIso()` de `AddExpenseModal.tsx`/`AddDebtModal.tsx`/`BetMonthDetailPage.tsx` usa `getFullYear()`/`getMonth()`/`getDate()` (fuso local do dispositivo) em vez disso. `StartBetMonthModal.tsx` já fazia certo (`currentYearMonth()`/`isFullyPast()`) - só copiar esse padrão em qualquer "data de hoje" nova.

## Autenticação

Token JWT salvo em `localStorage` (`financeiro_token`). Interceptor do axios em `api/client.ts` injeta o header e redireciona pra `/login` em qualquer 401. `AuthContext` chama `GET /auth/me` no boot pra restaurar sessão.

- **Mostrar/ocultar senha**: todo campo de senha (`LoginPage`, `RegisterPage`, `ResetPasswordPage`) usa o mesmo padrão — `<input>` dentro de um `<div className="relative">`, com `pr-11` no input pra abrir espaço, e um `button type="button"` (`icon-btn absolute right-1.5 top-1/2 h-8 w-8 -translate-y-1/2`) que alterna `type` entre `"password"`/`"text"` via um `showPassword` local. Ícones novos em `icons.tsx`: `EyeIcon`/`EyeOffIcon`.
- **Esqueci minha senha** (`ForgotPasswordPage.tsx`/`ResetPasswordPage.tsx`, rotas públicas fora do `ProtectedRoute`, ao lado de `/login`/`/register`): `ForgotPasswordPage` só pede o e-mail e chama `POST /auth/forgot-password` **diretamente via `api`** (sem passar por `AuthContext` — não gera sessão, não precisa de token) — sempre mostra a mesma mensagem de sucesso, nunca revela se o e-mail existe. `ResetPasswordPage` lê o token da URL (`useSearchParams().get("token")`) — o link vem de fora do app, de um e-mail de verdade — e chama `POST /auth/reset-password`; sem token na URL mostra direto uma mensagem de link inválido, sem tentar chamar a API.
